# 신뢰도 보강과 실전 계좌 연동 — 2026-09-19

## 후속 구현: 판단 검증실 (2026-09-19)

아래 1·2단계의 **재현/측정 기반**을 구현했다. 전체 PIT 인증·OOS 승격·실주문 구현 완료가 아니다.

- `portfolio_audit`: 판단에 사용한 전체 가격·날짜·보유·후보 유니버스·시그널 소비 필드·제약·비용과
  결과를 동결한다. SHA-256 주소 + 압축 SQLite 보관, 사용자/시장 범위, 내용 중복 저장 방지,
  읽기 무결성 검사. 원본 시그널 생성 엔진 전체를 재현하는 것은 아니며 소비한 필드만 기록한다.
- 현재 엔진 소스/NumPy 버전이 같을 때만 동결 입력 재계산을 허용한다. 버전이 바뀌면 이전 결과는
  보존하고 재계산은 보류한다. 과거 엔진 실행용 패키지 아카이브는 아직 구현하지 않았다.
- `exchange-calendars==4.13.2`의 XKRX/XNYS 일정과 버전을 보존한다. 마지막 완료 세션과 가격일을
  비교하며 휴장일·중복일·미래/미완료/낡은 마지막 가격은 행동계획/성과 측정을 보류한다.
  라이브러리 일정은 예정된 정규장 기준이며 임시 휴장·개별 거래정지·증권사 실거래 가능성을 인증하지 않는다.
- 분석/비교의 가격은 `load_portfolio_close_bundle`로 같은 캐시 세대의 날짜·가격을 함께 읽는다.
  기존 시그널용 잠정 실시간 호가 덧붙이기를 이 경로에서 제외했다. 시그널 자체는 관측 당시 값을
  소비하며 상위 시그널의 호가/공개시각 인증까지 완료된 것은 아니다.
- 평가 진입은 **판단 이후 아직 개장하지 않은 첫 세션의 종가**다. 장중 진단에서 이미 진행 중인
  세션을 진입 세션으로 쓰지 않는다. 21개 세션(진입 + 이후 20거래일)을 판단 당시 고정한다.
- `portfolio_counterfactual`: 같은 초기 보유·현금에서 **동결 계획 / 보유 유지 / 전량 현금화**를
  비교한다. 다음 세션 실제 관측 종가로 고정 수량에 비용을 적용하며 자금 부족이면 사후 수량 조정 없이
  보류한다. 평가는 매매비용 차감 후 미청산 NAV이고 배당·기업행동·추가 입출금은 포함하지 않는다.
- 세션 가격 누락 시 전일가 대체/날짜 건너뛰기를 금지한다. 기준 가격의 수정·누락은 보류하고,
  최초 관측한 미래 가격도 원자적으로 고정한다. 이후 수정 시 기존 평가를 덮어쓰지 않고 보류 기록을 남긴다.
- 평가 결과·가격 패널·가상 체결은 내용 주소별 append-only로 보관한다. 최신 조회 포인터만 갱신한다.
  같은 입력 재평가가 새 독립 표본을 만들지 않으며 겹치는 20일 창의 유의성/승률은 집계하지 않는다.
- 일별 스냅샷의 check+insert는 `BEGIN IMMEDIATE`로 원자화했다. 기존 중복 기록은 삭제하지 않는다.
  시장별 마감 작업자 분리는 아직 남아 있다.

### 화면과 API

포트폴리오의 **판단 검증실**은 기록 → 비교 → 실행 잠김의 세 영역을 구분한다.
최근 판단을 펼쳐 시점 보류 사유, 재현 검사, 새 비교 평가, 저장된 비교, 동결 입력을 확인한다.
기존 '데이터 신뢰도'는 **데이터 충족도**, 개별 권고 수익은 **참고 결과**로 바꿨다.
모바일은 세 영역을 세로로 배치하고 비교 표만 가로 스크롤한다. 수익률 차이를 승격/승인 색으로 칠하지 않는다.

- `GET /api/portfolio/decisions?market=kr|us`: 최근 10개 기록의 요약
- `GET /api/portfolio/decisions/{id}?market=...`: 본인 기록의 동결 입력/결과
- `POST /api/portfolio/decisions/{id}/replay?market=...`: 현재 동일 버전으로 재현 검사
- `POST /api/portfolio/decisions/{id}/compare?market=...`: 관측 가능한 종가로 비교 평가 후 보관
- `GET /api/portfolio/decisions/{id}/comparison?market=...`: 마지막 비교 평가 조회

추가 LLM/증권사 호출은 없다. 비용은 캘린더·배분 재계산 CPU 및 압축 SQLite 저장 공간이다.
새 판단 입력마다 전체 관련 이력을 보존하므로 저장량/백업 비용 모니터링이 필요하다. 최근 목록은 10개로
제한하지만 보존 기록을 자동 삭제하지 않는다. 평가도 현재 수동이며 자동 수집/알림은 후속 작업이다.

### 명시적으로 남은 것

`source_available_at_verified=false`, `bar_finality_verified=false`, `quote_verified=false`,
`oos_verified=false`, `live_eligible=false`를 유지한다. 수집 계층의 공개시각·확정봉 메타데이터,
기업행동/배당, 시장별 자동 마감 평가, 지속적 리밸런싱 전략 비교, 사전등록 OOS는 아직 완료하지 않았다.
다음 구현 단위는 이 메타데이터의 수집 연결 및 **주문 intent 원장/예약/UNKNOWN 대조**다.
실주문 전송 잠금은 계속 유지한다.

캘린더 참고: [exchange_calendars 공식 문서](https://github.com/gerrymanoim/exchange_calendars),
[XKRX 일정 구현](https://github.com/gerrymanoim/exchange_calendars/blob/master/exchange_calendars/exchange_calendar_xkrx.py).

## 후속 구현: 레퍼런스 봇 추종 정책 (2026-09-19)

실계좌 화면에서 안정형·균형형·공격형 **레퍼런스 페이퍼 봇** 중 하나를 고르고 다음 값을
사용자별로 저장할 수 있다.

- 봇 주문 금액의 추종 비율(기본 안정 25% / 균형 50% / 공격 75%)
- 주문당 최대 비중, 일일 매수 최대 비중, 종목 최대 비중, 최소 현금 비중

추종 비율은 주 수가 아니라 `레퍼런스 체결 수량 × 체결 기준가 × n% ÷ 내 지정가`로 환산한 뒤
내림한 정수 수량이다. 가격 갭 때문에 참조 봇보다 의도치 않게 큰 금액을 사지 않게 하기 위함이다.
1주에 못 미치면 보류한다. UI와 API 모두 계좌 소유자만 접근하며, 체결 수량·가격을 클라이언트가
보내지 않는다. 서버가 선택된 레퍼런스 봇 장부의 불변 거래 행 ID를 다시 읽는다.

`GET/PUT /api/live/copy-policy`, `GET /api/live/copy-events`,
`POST /api/live/copy-preview`가 제공된다. 마지막 API는 15분 이내의 참조 체결만 사전점검하고,
과거 체결은 성과 참고값으로만 취급한다. 추종 정책 저장은 KIS 자격증명이나 주문 권한을 받지 않는다.

현재 사전점검은 주문당·종목·최소 현금 한도를 계산한다. **일일 매수 한도는 아직 통과로 표시하지
않는다.** 증권사 당일 조회만으로는 본 서비스가 예약한 현금/수량, 부분체결, 타임아웃의 UNKNOWN을
정합하게 대조할 수 없기 때문이다. 따라서 정책 수치가 모두 맞아도 `copy_preview_only`,
`order_transmission_enabled=false`이며 주문을 만들거나 전송하지 않는다.

남은 3단계 주문 원장은 (a) 참조 이벤트와 결정 ID로 생성한 불변 intent, (b) 원자적 현금·매도가능
수량 예약, (c) 접수/부분체결/완료/취소/거절/UNKNOWN 전이, (d) 증권사 조회 대조와 재전송 금지,
(e) 일일 한도 집계를 하나의 트랜잭션으로 구현해야 한다. 이 완료 및 실행 전 게이트/OOS 승격 전에는
이 설정을 실주문 활성화 장치로 사용하지 않는다.

## 이번 배포의 경계

실전 계좌를 **조회하고 주문 여력을 검사하는 연결 기반**이다. 실주문 활성화 배포가 아니다.
기존 페이퍼 봇/레퍼런스 장부는 유지하며 실계좌 주문과 연결하지 않는다.
복수 계좌·환율·계좌별 세금 최적화는 범위 밖이다. 초기 어댑터는 기존 KIS 국내 현물 코드를 사용했다.

- `KIS_ENV=demo|real`만 허용한다. `prod` 등 오타는 실패 처리한다.
- `real`의 주문 함수와 저수준 비-GET 전송은 모두 차단한다.
- `ALLOW_REAL_ORDERS=true`도 이 빌드의 차단을 해제하지 않는다.
- `/api/live/orders` 같은 주문 전송 API는 없다.
- 계좌 조회는 로그인 이메일이 `KIS_ACCOUNT_OWNER`와 일치해야 한다. 관리자 권한만으로 우회할 수 없다.
- 실제 인증정보/계좌 조회/주문을 사용한 검증은 수행하지 않았다. 모의 응답과 합성 데이터로 검증했다.

## 수정한 신뢰성 결함

1. 메타 모델은 종목별 배열 위치 대신 공통 날짜 축으로 분할하고, 같은 세션은 같은 fold에 둔다.
   진입은 기존 accuracy 규약과 같이 신호 다음 거래일 종가로 변경했다. 과거 shadow 수치는 새 규약으로
   재평가해야 하며, 이것만으로 정책 승격을 허용하지 않는다.
2. 리스크 패리티 반복식을 convex risk-budget 좌표하강으로 바꾸고 잔차를 확인한다.
   수렴하지 않은 결과는 반환하지 않는다. 이후 cap 적용은 별도 단계이므로 최종 비중을 순수 ERC 해라 주장하지 않는다.
3. 고상관 묶음 한도를 목표배분과 최종 계획 검사에 포함한다.
4. 신규 후보와 기존 보유는 `portfolio_decision.decide`에서 함께 배분하고 하나의 현금 원장을 사용한다.
   후보 표의 금액은 동일 행동계획의 일부이며 독립적인 추가 지출안이 아니다.
5. 보유 평가액/이력 결손, 부분 상관 결손, 상수 가격, 비유한 값, 날짜 중복/불일치에서 보류한다.
   후보 상관과 변동성은 최근 60개 수익률을 사용한다. 최종 기준일 일치는 절대 신선도 인증을 의미하지 않는다.
6. BUY 확인이 없는 확대는 차단한다. 최소 현금은 비용을 내기 전에 예약한다.
   비용과 정수 수량 반영 후 종목·섹터·묶음·현금 한도를 다시 검사하며 위반 계획은 노출하지 않는다.
7. LLM 비스트리밍 도구 호출의 미정의 `purpose`로 성공 응답/사용량이 유실되는 문제를 수정한다.
8. 신규 권고에 완전한 비용 가정을 저장하고 사후 청산 계산에 재사용한다.
   비용 가정이 없는 과거 권고의 순수익은 미확인으로 표시하며 현재 설정으로 추측하지 않는다.
   화면의 매수는 비용 후 수익, 매도는 비용 미반영 가격하락 회피 지표로 구분한다.

## 연결 화면과 API

실보유 포트폴리오 영역의 접이식 **KIS 실전 연결 준비** 카드:

- 연결 상태: `GET /api/live/status`
- 잔고·당일 KRX 주문 조회: `POST /api/live/account`
- 지정가 주문 여력 사전조회: `POST /api/live/preflight`

서버 환경변수(값을 문서/채팅/커밋에 넣지 않는다):

`KIS_APP_KEY`, `KIS_APP_SECRET`, `KIS_ACCOUNT_NO`, `KIS_ACCOUNT_PRODUCT_CD`,
`KIS_ENV`, `KIS_ACCOUNT_OWNER`.

소유자가 서버의 비밀 설정으로 직접 구성한 뒤 조회 화면에서 확인한다. real 전환은 조회만 허용한다.
주문 가능 금액은 예수금/순자산 역산이 아니라 KIS의 `nrcvb_buy_amt`, `nrcvb_buy_qty`를 사용한다.
매도는 보유 수량과 매도가능 수량을 구분한다. 매도가능 수량을 받지 못하면 보류한다.

토큰은 환경·앱키·키 교체·계좌별로 분리하고 파일 권한 0600으로 저장한다.
기존 무구분 `kis_token.json`은 삭제하지 않지만 재사용하지 않는다. 첫 조회에서는 새 토큰 발급이 필요할 수 있다.
현재 발급 락은 단일 프로세스용이다. 다중 프로세스 운영 전에 분산 토큰 발급 조정이 필요하다.

잔고/주문은 연속조회가 모두 끝나야 완전한 응답이다. 뒷 페이지 실패·반복 커서·최대 페이지 초과는 실패한다.
미체결·부분체결·불명 주문이 있으면 추가 주문 여력 판정을 보류한다. 실패를 빈 계좌나 주문 0건으로 바꾸지 않는다.
동시 수동 계좌 조회는 429로 거절한다. 이는 전체 증권사 호출의 전역 rate limiter를 대체하지 않는다.

`broker_checks_passed=true`는 **조회한 계좌의 여력**만 통과한 상태다. 항상 `ready=false`,
`order_transmission_enabled=false`이며 투자정책/주문 승인을 뜻하지 않는다.
시세 신선도·휴장/세션·호가 단위·주문 한도·손실 한도·권고 만료를 인증하지 않았기 때문이다.

공식 규약 확인 출처:

- [한국투자증권 Open API](https://github.com/koreainvestment/open-trading-api)
- [매수가능 조회](https://github.com/koreainvestment/open-trading-api/blob/main/examples_llm/domestic_stock/inquire_psbl_order/inquire_psbl_order.py)
- [일별 주문체결 조회](https://github.com/koreainvestment/open-trading-api/blob/main/examples_llm/domestic_stock/inquire_daily_ccld/inquire_daily_ccld.py)

## 실주문 전에 남은 작업 (순서 유지)

1. **공통 시점 스냅샷**: 확정봉/호가 분리, 거래소 캘린더, 정보 이용 가능 시각, 데이터/정책 버전,
   권고 시각과 체결 가능 시각, 전체 데이터 재현용 아티팩트. 현재 결정 해시는 전체 데이터 원장을 대체하지 않는다.
2. **포트폴리오 반사실 원장**: 동일 초기 자산에서 유지/단순 정책/신규 정책의 비용 후 NAV 경로 비교.
   현재 개별 권고 1/5/20일 결과는 이 검증이 아니다. 일별 스냅샷 중복의 원자성·시장별 마감 작업도 보강한다.
3. **주문 수명주기 원장**: 결정 ID+계좌+주문 intent의 고유키, 현금/수량 예약, 제출 전 영속화,
   접수·부분체결·완료·취소·거절·상태 불명 전이. 타임아웃은 실패가 아니라 UNKNOWN으로 유지하고
   재전송 전 반드시 증권사 원장과 대조한다. exactly-once 체결을 주장하지 않는다.
4. **실행 전 게이트**: 소유자 확인, 증권사 선택, 종목/시장/세션, 최신 호가, 지정가/추격 허용폭,
   주문당/일별 총액, 위험 증가와 위험 축소 구분, 미체결 예약, 일손실 제한, 비상 정지.
   한도는 사용자가 정하고 키/설정 변경만으로 활성화되지 않게 한다.
5. **알림 배송 원장**: 사용자/수신자별 상태, 작업 점유, 부분 실패 재시도, 권고 만료/취소,
   설명 LLM 실패 시 결정론적 위험 안내. 현재 공용 텔레그램 outbox를 개인 실계좌 알림에 그대로 쓰지 않는다.
6. **승격**: 정합성·장애/재시작·모의 체결 검증, 미관측 OOS, 비용/지연 스트레스, 사용자 검토 이후
   제한된 사용자 승인 주문 경로를 별도로 설계한다. 자동 주문 활성화와 실제 거래는 이번 작업에 포함되지 않는다.

추가 보류: LLM 동시 호출 예산 예약/정산, 실측 성공확률 보정, 기대수익 기반 신규편입 최적화,
스케줄러/작업자 분리. 현재 통합 배분은 위험배분 기준 정책이지 수익률 최적 정책이 아니다.

## 2026-09-26 순차 구축 현황 (실주문 잠금 유지)

- 토스 실보유 조회가 분석용 수동 보유내역을 자동으로 덮어쓰지 않는다. 명시적 복사만 허용한다.
- 실보유 관측 원장은 KRW/USD 평가액과 당일손익을 분리 저장한다. 현금·입출금·실현손익이 없으므로
  그래프는 **보유주식 관측**이며 계좌 전체 NAV/TWR 또는 전략 수익률이 아니다.
- 토스 계좌 목록의 `accountSeq`와 서버 설정값을 대조한 뒤 매수가능액, 진행 중 주문,
  매도가능수량을 GET으로만 읽는다. 계좌번호·토큰은 API/UI에 반환하지 않는다.
- `broker/intent_ledger.py`에 참조 체결 15분 유효성, 동일 이벤트 중복 차단, SQLite 원자적
  현금/수량·일일 매수예산 예약, 상태/감사 이벤트, UNKNOWN 보존, **이미 알려진** 주문 ID의
  GET 상세 대조를 구현했다. 이 원장은 준비용 내부 모듈이며 사용자가 주문을 만들거나 전송하는
  API/UI/작업자는 없다. 토스 `clientOrderId` 멱등성은 10분에 한정되어, 응답이 유실되고
  증권사 주문 ID도 없는 UNKNOWN은 자동 재전송·자동 해제할 수 없다.

실주문 경로의 남은 필수 조건: 동일 계좌의 현금 포함 총자산과 입출금/체결 원장 확보,
레퍼런스 이벤트/결정 아티팩트와 실제 계좌를 결합하는 사전검증 경로, 일손실·가격·세션·시장
리스크 게이트, 브로커 미체결 주문과 로컬 예약의 대조, UNKNOWN 수동 해결 운영 절차,
OOS/장애 검증, 소유자의 개별 주문 승인. 이 조건 전에는 `order_transmission_enabled=false`다.

## 검증 원칙

테스트 통과는 수익성 입증이 아니다. 합성 반례를 회귀 검사에 추가하고, 실제 운영/증권사 응답은 별도 확인한다.
화면은 합성 응답을 제공하는 격리 서버에서 390px/1512px 레이아웃·조회 동작·콘솔 오류를 확인한다.
실계좌 인증정보를 로드하는 앱 서버나 실주문 API를 검증 목적으로 실행하지 않는다.

## 2026-09-27: 국내 지정가 소액 수동 주문 파일럿

앞의 2026-09-26 잠금 설명은 당시 배포 상태다. 이번 변경은 **토스 실계좌 소유자가
주문마다 직접 확인하는 좁은 경로**만 추가한다. 자동 봇 복사, KIS 실주문, 미국주식,
시장가, 정정·취소 API는 여전히 제공하지 않는다. 수익성/OOS 검증이 끝났다는 의미도 아니다.

- 기본값은 비활성이다. 운영에서 `TOSS_MANUAL_ORDER_ENABLED=true`와 Railway 영속 볼륨
  `RAILWAY_VOLUME_MOUNT_PATH=/app/data`가 확인돼야 열리며, 볼륨은 실제 `/app/data`에
  마운트해야 한다. SQLite 주문 원장이 재배포 때 사라지는 상태에서는 전송을 허용하지 않는다.
- 저장된 봇 성향의 15분 이내 KR 참조 체결만 사용한다. 매수 안전 게이트, 토스 계좌 식별,
  정규장 연속매매 시간, 30초 이내 시세, 지정가의 현재가 대비 불리한 방향 0.5% 이내,
  보유/현금 매수가능액/진행 중 주문을 매번 다시 확인한다. 미체결 주문이 하나라도 있으면 보류한다.
- 국내 보유주식 평가액+현금 매수가능액을 **보수적 위험 기준금액**으로 사용한다. 이는 총자산/NAV가
  아니다. 사용자 주문·종목·최소현금·일일매수 한도와 함께 주문당 10만원, 앱 매수 일일 20만원의
  절대 상한을 적용한다. 미수·환율 환산·복수 계좌는 사용하지 않는다.
- 미리보기에서 불변 intent와 60초 승인 바인딩을 저장한다. 소유자가 화면의 종목·방향·수량·가격
  전체를 다시 입력하고 확인해야 한다. 제출 직전 동일 검증을 반복하고 SQLite 트랜잭션으로
  `SUBMITTING`을 먼저 기록한 뒤 `clientOrderId`를 넣어 **한 번만** POST한다.
- 타임아웃·오류·응답 누락은 UNKNOWN이며 자동 재시도하지 않는다. 주문 ID가 있으면 GET 상세로
  대조하고, ID가 없으면 토스 앱을 통한 수동 확인이 필요하다. 화면에는 최근 주문 원장이 남는다.
  현재 앱에는 실주문 취소/정정이나 UNKNOWN 수동 해제 API가 없다.
- 주문 전송의 실계좌 통합 테스트는 수행하지 않는다. 합성 HTTP 응답과 장애/중복 테스트만 수행하며,
  실제 활성화·최초 소액 주문 전 운영자가 계좌/볼륨/허용 IP/시각·미체결 상태를 직접 확인한다.
